2026-11-25 (12) FULL-SPEED USB BULK STREAMING (0.1-0.2 fps ->
12-20 fps; kills the "usbcast: ACK timeout — resending" spam).
Round 11 gave a perfect link — cold-boot enumeration, the 'R'
handshake, KDE Wayland casting all worked — but frame streaming
crawled: 0.1-0.2 fps and the frame counter jumping 2 -> 3 -> 9 ->
12 -> 13 -> 15. THREE stacked root causes:

STEP 1 — THE DIAGNOSIS:

  (a) TIMER-TICK STALL IN THE BULK RX FILL (the big one). A
      40,969-byte frame is 641 64-byte bulk packets. usb_fill()
      (src/natives.c, the comm:usb InputStream fill loop) called
      fp_sleep_ms(2) after EVERY partial drain — and on target
      fp_sleep_ms() -> fpdoom's sys_wait_ms() busy-waits on the
      hardware timer at 0x8100300c, where a 2 ms request
      quantizes to a FULL timer tick (~10-16 ms, user-measured on
      the real phone). Hundreds of ring refills later that is
      >5 seconds per frame; the 2048-byte usb_buf ring sits
      starved, EP2 OUT NAKs packet after packet, and the host
      watches its 5 s ACK_TIMEOUT_MS expire mid-transfer.

  (b) HOST ACK TIMEOUT -> FRAME DESYNC. Once the timeout fired,
      usbcast_host.py resent a NEW "FPJ2" header into the middle
      of the still-arriving old frame, so UsbCast.jar burned CPU
      scanning byte-by-byte for the next sync point — a slow
      spiral on BOTH sides of the wire.

  (c) PIPEWIRE QUEUEING LATENCY. While usbcast_host.py blocked on
      the phone's 'K' ACK, GStreamer's pipewiresrc kept pushing
      desktop frames into an unbounded queue in front of
      videoconvert; fdsink fed us the PAST, frame after frame.

STEP 2 — THE PHONE FIX (src/natives.c usb_fill(), three-phase
  state machine; fp_platform.c Round-12 section documents the
  transport contract; fpdoom files, the Round 7 LCD pipeline and
  Round 11 fp_usb_init() untouched):

    ACTIVE (first byte of the read seen, rem > 0): tight spin over
      fp_usb_read(dst+got, len-got) — NO fp_sleep_ms at all. Each
      call is already "spin-poll usb_check_int() + usb_read(p, rem,
      0)": fpdoom's usb_read(..., USB_NOWAIT) services the UDC
      interrupt handler (EP0 control transfers included) whenever
      the 2 KB ring has >= 64 bytes free, then drains the ring to
      EMPTY before returning. One loop pass is microseconds on
      the 208 MHz ARM926 — the ring never wedges full, the host
      NAKs at most one pass, and full-speed bulk (64-byte packets
      every ~60 us of wire time) is drained essentially as it
      arrives.

    KEYPAD/EXIT POLLING at a ~16 ms cadence (FPJ_USB_KEY_POLL_MS,
      gated on fp_time_ms() == sys_timer_ms()): midp_paint_pump()
      plus a re-check of the close() abort flag every ~16 ms of
      streaming. The exit key (RSOFT) still breaks any blocked
      bulk read — bounded by one poll period — without
      per-packet pump overhead. The abort check at the loop top
      plus the post-pump recheck close the race where keyPressed
      -> close() lands mid-pump.

    IDLE (not one byte of this read yet): the ONLY remaining
      yield — midp_paint_pump() + fp_sleep_ms(2). This is the
      sanctioned pre-first-byte wait AND it keeps Round 11's EP0
      enumeration service alive (fpj_usb_pump() runs from the
      sleep path while no reader owns the ring). The ~10-16 ms
      quantization here costs nothing: it is the inter-frame gap
      (the host only starts the next frame after our 'K').

  Why the loop lives in natives.c and not fp_platform.c: the host
  check mock pipe is synchronous — a platform-side blocking
  primitive would need a parallel mock implementation that the
  host tests would never actually execute against the real loop.
  usb_fill() in natives.c compiles VERBATIM for host and target,
  so the 311 host checks exercise the exact production code. The
  fp_usb_read() platform primitive keeps its signature and its
  drain-to-empty semantics (documented in platform.h).

STEP 3 — THE HOST FIX (tools/usbcast_host.py; base = the user's
  own Round 11 edit, PRESERVED: the merged --kde D-Bus ScreenCast
  portal mode, the --portrait flag, the per-interface kernel-
  driver detach loop and the EBUSY-safe set_configuration()):

    gst-launch-1.0 pipewiresrc fd=.. path=.. ! video/x-raw
      ! queue max-size-buffers=1 leaky=downstream
      ! videoconvert ! videoscale ! video/x-raw,format=RGB,...
      ! fdsink fd=1

  The leaky queue is the host half of the fix: while cast_loop()
  blocks on the phone's 'K' ACK, pipewiresrc keeps producing; the
  queue (max-size-buffers=1, leaky=downstream) DROPS the older
  queued buffers as new ones arrive, so fdsink always emits the
  freshest desktop frame the moment we are ready to send. No
  backlog, no stale frames, no latency creep.

2026-11-25 (11) COLD-BOOT USB ENUMERATION — fpj2me.bin booted from
microSD via sdboot NEVER appeared in lsusb/dmesg when plugged into
Linux (Round 10's pipe only worked when the app itself had been
loaded over USB by the FDL host). Root cause had TWO independent
parts, both diagnosed from the OEM firmware (flash.bin) + the leaked
SC6531E/M Device Specification:

STEP 1 — THE DIAGNOSIS (sources: stock flash.bin XIP-disassembled,
  cross-checked against the SC6531E DS, both provided by the user):

  (a) usbio.c line 22-24 says it out loud: "not necessary, because
      USB is already initialized by the bootloader". That is true
      ONLY for the LIBC_SDIO<3 FDL path — the host loaded us over
      USB, so BootROM/FDL1 left the UDC powered and armed. entry.c
      calls usb_init() exclusively inside `#if LIBC_SDIO < 3`
      (entry.c:171); with LIBC_SDIO=3 (mandatory for sdboot) NOTHING
      in the image ever touches USB. usb_check_int() polls INTC1
      raw bit 5 (0x80001004) — polling machinery is fine, it is the
      bring-up that is missing.

  (b) Even calling usb_init() alone would hang or stay invisible:
      cold, the SC6531E USB island is POWERED DOWN. Three gates are
      off: the AHB power island (USB sits on the AHB matrix at
      0x90000000-0x97FFFFFF, DS 5.2.1), the module control bit, and
      LDO_USB33 — the analog-die LDO that biases the PHY AND the
      1.5 k D+ pull-up. No pull-up = no attach = the host's hub
      sees literally nothing (not even "unknown device").

  (c) THE OEM SEQUENCE (recovered from the phone's own firmware:
      flash.bin, XIP NOR so file offset == vaddr; UDC cold init at
      0x29FFA, called from the UDC-service wrappers at 0x2A0AA/
      0x2A2B2; LDO helper at 0x29B04; ADI helpers 0x6E52/0x6ED2):

        [0x20501080] = 0x10       ; AHB power-enable SET, bit 4 = USB
        [0x8B000220] |= 0x20      ; GR module-control bit 5
        <notify + delay 300 ms>   ; island settle (0x2A020: counter
                                 ; busy-wait of 300 ms units)
        [0x90000000] |= 2         ; USB_CTRL.SELF_PWR (DS 6.1.4.2.1:
                                 ; "software should write 1 ... since
                                 ; our USB device is always self-
                                 ; powered")
        [0x90000000] |= 1         ; USB_CTRL.USB_EN
        EP0 (0x64): max-pkt 8 + INT_CLR 0x3FFF + INT_CTRL |= 1<<8
                   + buffer-ready bit 28   (0x2A036-0x2A054 + 0x29B2A)
        EP1 (0xC0), EP2 (0x100), EP3 (0x140), EP4 (0x180) armed with
                   the same bit vocabulary as fpdoom's usb_init()
                   (0x29B66/0x29BC6/0x29C0C/0x29C56)
        LDO_USB_REG0 bit0 = 0     ; 0x29B04(r0=1): adi RMW
                                 ; 0x8200147C: LDO ON -> D+ pull-up
                                 ; powered -> THE HOST SEES ATTACH
      The LDO helper is a plain ADI read-modify-write: r0!=0 clears
      bit 0 (power on), r0==0 sets bit 0 (power down — used by the
      charger path at 0xC612 and as the FIRST call of cold init,
      i.e. a soft-disconnect while reconfiguring).

      Datasheet cross-checks: LDO_USB_REG0 = Glb-reg offset 0x7C,
      analog die, ARM-side ADI window 0x82001400+ (DS 5.2.6.1/13.1.1
      register map, 13.1.1.32 bit fields: bit0 LDO_USB_PD 1=pd/0=on,
      bit1 SHPT_PD, bit8 LP_EN_SW; LDO_USB_REG1 0x80 = voltage,
      default 0x12 is fine). FIFOs at +0x80000 (6.1.4.1) match
      usbio.c. Pin_CTRL_REG2 usb_uart1_sel (DS 3.5.2.3) defaults to
      0 = USB DP/DM stay USB — the stock fw never touches it, and
      neither do we. The stock fw also never writes Pin_CTRL_REG0
      USB_PORN (0x402A0000 bit 0) — left at its reset default, so we
      leave it too.

STEP 2 — fp_usb_init() (src/fp_platform.c, Round 11 section):
  Idempotent, no fpdoom file touched:
    1. [0x20501080] = 1<<4 and [0x8B000220] |= 1<<5  (idempotent
       SET/RMW: safe even under a live FDL session)
    2. sys_wait_ms(300)  — the stock settle delay
    3. ADOPT-IF-LIVE: if USB_CTRL.USB_EN reads 1, entry.c's FDL path
       already armed the controller and the host session is live ->
       return success WITHOUT touching LDO or endpoints (never
       reset endpoints under a host).
    4. cold path: adi_write(0x8200147C, read|1)  — LDO off
       (soft-disconnect while re-arming, exactly the stock order)
    5. USB_CTRL |= SELF_PWR, then |= USB_EN
    6. usb_init()  — fpdoom's proven EP0/EP2/EP3 arming, which is
       register-for-register the stock sequence (max-pkt 8/64/64,
       per-EP int enables, INT_CLR 0x3FFF, buffer-ready, EP-enable,
       TIMEOUT_LMT=15) AND zeroes the 2 KB RX ring
    7. adi_write(0x8200147C, read & ~1)  — LDO on: D+ pull-up
       powered, host sees 1782:4d00 and enumerates

2026-11-25 (10) USB SCREEN CASTING — the phone as a live 128x160
LINUX MONITOR (UsbCast.jar + tools/usbcast_host.py). Goal: run a
lightweight MIDlet inside fpj2me that receives raw RGB565 frames over
USB and displays them in real time, with ZERO per-pixel math and ZERO
per-frame allocation in Java bytecode on the 208 MHz ARM926.

STEP 1 — WHAT FPDOOM'S USB LAYER ACTUALLY IS (inspected, not assumed):
  fpdoom compiles usbio.c into our image (SYS_SRCS in
  build_sc6531.make) and exposes exactly three primitives:
    int  usb_read(void *dst, unsigned len, int wait)
    int  usb_write(const void *src, unsigned len)
    int  usb_getchar(int wait)
  The DEVICE side was already configured by the phone's bootloader:
  vendor-class 0xFF, VID 0x1782 / PID 0x4D00, 64-byte bulk packets,
  EP OUT 0x02 (phone receives) and EP IN 0x83 (phone transmits), RX
  side a 2 KB ring in usb_buf. With LIBC_SDIO=3 nothing else in the
  image touches USB (the libc_server handshake and _debug_msg are
  compiled out in libc.c), so the pipe belongs to the MIDlet while a
  StreamConnection holds it. We deliberately NEVER call usb_init():
  re-running the endpoint init would reset live state under an
  enumerated host.
  HOST SIDE: no kernel driver binds to a vendor-class device, so the
  Linux sender talks to the endpoints directly with libusb (pyusb),
  NOT /dev/ttyACM* or /dev/ttyUSB* — there is no CDC ACM function.
  USB permissions: install the udev rule below once, or use sudo.

STEP 2 — THE TRANSPORT, PLUMBED LIKE THE REST OF fpj2me:
  platform.h gained a 4-call HAL surface; fp_platform.c implements
  them over usbio (fp_usb_read = one non-blocking drain that also
  services EP2 interrupts, fp_usb_write = blocking 64-byte-chunked
  TX, fp_usb_available, fp_usb_reset). hostcheck provides the same
  surface as a mock FIFO. NO LCD CODE WAS TOUCHED (the Round 7
  pipeline stays locked).
  src/natives.c maps it into MIDP:
    javax.microedition.io.Connector.open("comm:usb")
      -> StreamConnection stub object (any other URL throws the
         MIDP-mandated ConnectionNotFoundException; Connector.
         openInputStream/openOutputStream convenience forms too)
    sc.openInputStream()  -> java/io/InputStream  (slot 4 = usb mode)
    sc.openOutputStream() -> java/io/OutputStream (slot 0 = usb mode)
    OutputStream.write(I)/([B)/([BII) -> the wire (the 1-byte ACK)
  EXIT-KEY LIVENESS (the "always break out of a USB wait" law): the
  InputStream carries an abort flag (slot 5); close() sets it and
  every blocked native read polls it while pumping the frame pump
  every ~2 ms — so keyPressed(-7) -> in.close() interrupts a read
  from the INSIDE, UsbCast returns, notifyDestroyed hands control
  back to the launcher menu. No battery pull, ever. Reads never
  return a spurious -1: -1 is reserved for close()/link-EOF (a slow
  host is never mistaken for a dead one).
  THE FAST BLIT — com.nokia.mid.ui.DirectGraphics.drawPixels:
    drawPixels(byte[] pixels, null, offset, scanlength, x, y, w, h,
               0, 565 /*TYPE_USHORT_565_RGB*/)
  is now a registered native: for the identity manipulation it calls
  the new gfx_draw_rgb565 (src/midp_graphics.c) — one memcpy per
  clipped row from the Java byte[] straight into the target's RGB565
  buffer. 40,960 bytes per frame with no per-pixel math, no
  allocation, no GC churn (full fidelity too: an exact 0x0000 stays
  0x0000 — no PX_TRANS remap; a cast frame may legitimately be pure
  black). fpj2me's documented interpretation of the byte[] overload:
  `offset` is a BYTE offset (the cast payload starts at buf[9],
  behind the 9-byte header) and pairs are little-endian — exactly the
  wire format, so the copy is layout-identical on the ARM926.
  Other formats/manipulations/non-null masks degrade to silent
  no-ops per project policy.

STEP 3 — THE FRAME PROTOCOL (self-syncing, ACK-paced):
  host -> phone, per frame:
    "FPJ2" | u16le width=128 | u16le height=160 | u8 flags=0
           | 128*160*2 bytes little-endian RGB565 payload
  phone -> host:
    'R' (0x52) once, when UsbCast boots ("ready")
    'K' (0x4B) after each frame is DISPLAYED (the host waits for it:
    backpressure paced to exactly what the phone can render)
    'Q' (0x51) when the MIDlet exits (exit key) — the host stops
  Mid-stream connects resync trivially: the MIDlet scans byte-by-
  byte for the "FPJ2" magic and only accepts 128x160/flags=0
  headers (anything else drops back to the scan). USB NAK
  backpressure (2 KB ring) means the host physically CANNOT
  overflow the phone — a frame is either delivered whole or the
  hardware holds the rest.

STEP 4 — UsbCast.jar (tools/make_usbcast_jar.py, javac-free):
  UsbCast (MIDlet) + CastScr (Canvas), hand-assembled classfiles in
  the make_test_jar.py style. CastScr allocates ONCE in <init>: a
  40,978-byte frame buffer (9 header + 40,960 payload), a mutable
  Image, its Graphics, and the DirectGraphics handle — then the run
  loop does only control flow: scan magic, readN(4,5) header,
  validate 128x160, readN(9,40960) payload, dg.drawPixels(buf,
  null, 9, 128, 0, 0, 128, 160, 0, 565), repaint() +
  serviceRepaints(), out.write('K'). paint() draws the status screen
  ("USB CAST / WAITING FOR USB") until the first frame arrives, then
  the latest frame via drawImage. keyPressed(-7) = closed=true +
  in.close() = the guaranteed exit. The jar boots from the launcher
  menu like any game (copy it into the fpj2me SD folder next to the
  others; fp_menu.c lists every *.jar in the directory).

STEP 5 — tools/usbcast_host.py (the LINUX sender):
  python3 + pyusb (sudo pacman -S python-pyusb libusb); numpy used
  if present (0.05 ms/frame RGB24->RGB565), pure-Python LUT
  fallback keeps up with the USB ceiling regardless.
    --demo    animated bars + moving box + FPS counter (link test
              with zero capture setup)
    --stdin   raw RGB24 128x160 (or 160x128 + --rotate cw/ccw —
              rotation via numpy rot90 or a per-pixel strided copy)
    --fps N   rate cap (default: as fast as the phone ACKs; USB
              full-speed bulk tops out ~12-20 fps at this size)
    --device VID:PID override, --no-hello, --selftest (encoder +

Integration with your sdboot phone (nothing gets re-flashed)
------------------------------------------------------------
sdboot boots fpbin/fpmain.bin from the FAT32 card; fpmenu reads
fpbin/config.txt and launches app binaries from the card. fpj2me is
just another app. One-time:

  1. clone fpdoom:      git clone https://github.com/ilyakurdyukov/fpdoom
  2. copy this dir in:  cp -r fpj2me /path/to/fpdoom/
  3. build:             cd /path/to/fpdoom/fpj2me
                        make LIBC_SDIO=3 CHIP=1 TOOLCHAIN=<arm-prefix>
     (LIBC_SDIO=3 = SD-card file IO, MANDATORY for sdboot apps;
      CHIP=1 = SC6531E. TOOLCHAIN is the arm-* prefix of your cross
      gcc — e.g. TOOLCHAIN=arm-buildroot-linux-gnueabi with its bin/
      on PATH. You get fpj2me.bin.)
     A prebuilt fpj2me.bin from THIS exact tree (GCC 15 armv5-eabi
     soft-float, LIBC_SDIO=3 CHIP=1, two-stage fpdoom image verified by
     disassembly: part2 stub -> part1 reloc -> libgcc soft-float
     linked) ships next to this README — you can copy it to fpbin/ and
     test before building. Toolchain note: the VM's float/double
     opcodes need the ARM soft-float helpers (__aeabi_dadd,
     __aeabi_fmul, ...); fpdoom links -nostdlib and some toolchains
     do not pull libgcc in by themselves. THIS Makefile already links
     libgcc AFTER the objects in its own part2 rule — you need no
     extra flags. If your link ever reports __aeabi_* undefined, your
     build is not using this Makefile's rule (stale objects or an old
     tree copy): make clean and rebuild.
     Toolchain note 2: the NEWLIB bare-metal toolchains (arm-none-eabi,
     GCC 16+) default to emulated TLS, and stb_image's thread_local
     globals then pull libgcc's emutls.o -> undefined malloc/abort.
     The tree already defines STBI_NO_THREAD_LOCALS in BOTH stb-using
     TUs (vendor/stb_impl.c and src/midp_image.c) — single-threaded by
     design, so plain statics are correct. If you re-vendor stb,
     keep that define.
  4. SD card (same layout as your other fpdoom games):
        fpbin/fpj2me.bin             <- the built binary
        games/fpj2me/*.jar           <- as many jars as you like
                                       (128x160 builds! menu lists them)
        games/fpj2me/rms/            <- optional: per-jar RecordStore
                                       saves. NOT required: with no
                                       mkdir in the fpdoom libc the
                                       runtime falls back to flat
                                       rms_<jar>_<store>.rms files in
                                       the same folder
     No .jad files needed: the MIDlet-1 entry class is read from each
     jar's own META-INF/MANIFEST.MF (the JAD is optional in MIDP).
  5. add to fpbin/config.txt (same pattern as your other games):
        |Java games| fpbin/fpj2me.bin $@ --dir games/fpj2me
     (binaries live in fpbin/, data in games/<name>/ — like retris)
     ONE fpmenu entry now covers every jar you drop into the folder.

     *** THE $@ RULE (verified against fpmenu's readconf.h) ***
     The FIRST non-empty, non-comment line of config.txt is NOT a
     variable definition — it is the argument list fpmenu stores in
     the $@ variable and prepends to every app it launches:
        --bright 50 --charge 2
     Keep the line exactly like that. If your first line reads
     "$fpj2me = fpbin/fpj2me.bin $@" instead, fpmenu parses that TEXT
     as $@'s value, $fpj2me never becomes a defined variable, and the
     menu entry silently stops working (fpmenu looks for a FILE
     literally named "$fpj2me" and finds nothing). Variables go BELOW
     the first line. A ready-to-use config.txt ships in sdcard/ of
     this tree — see sdcard/config.txt.

Everything is read with RELATIVE paths because fpmenu's --dir makes

class -> startApp().

libc_server over USB to see fp_dbg() logs (with LIBC_SDIO=3 the USB
log channel is off; panics still show a red screen).

Troubleshooting: what the screen tells you (one color per stage)
------------------------------------------------------------------
  IMPORTANT — the backlight contract: fpmenu switches the backlight
  OFF the instant it launches any app binary; the ONLY thing that
  switches it back on is fpj2me's own sys_start(), which now runs
  BEFORE the first paint of the blue banner. So the color you see
  (or don't see) tells you exactly how far execution got:

  BLACK + backlight OFF  -> fpj2me.bin never executed a single
     (nothing at all)      instruction of ours — the backlight never
                           came back. The image was not loaded or not
                           started. In order of likelihood:
                           1. The fpj2me.bin on the card is truncated
                              or not the file you think: fpmenu's
                              loader loops FOREVER (black, no
                              backlight) when the FAT cluster chain
                              yields fewer bytes than the directory
                              entry promises. On the PC, compare the
                              byte size of the card copy with the
                              built file — they must match EXACTLY —
                              then recopy, eject the card cleanly
                              (no cached writes), and reinsert.
                           2. Wrong path/name: the fpbin/config.txt
                              line must read
                              |Java games| fpbin/fpj2me.bin $@ --dir games/fpj2me
                              and the binary must be at fpbin/fpj2me.bin
                              (binaries in fpbin/, jars in games/fpj2me/).
                           3. A build that mislinked (soft-float stubs,
                              wrong start layout): rebuild with THIS
                              tree's Makefile (libgcc linked for you)
                              and re-copy the new file.
                           4. Card hygiene: FAT32 only (no exFAT), and
                              a badly fragmented card can break the
                              cluster chain — copy the files onto a
                              freshly FAT32-formatted card in one pass.
                           NOTE: if the phone shows fpmenu again
                           instead, the app ran and failed BEFORE
                           sys_init (e.g. --dir not found — that path
                           is now case- and spelling-exact) and the
                           watchdog rebooted it: check the config line.
  BLACK + backlight on  -> fpj2me.bin is running but the LCDC scans
     out nothing. Fixed in this tree: lcd_appinit() must assign
     sys_data.display.w2/h2 UNCONDITIONALLY (fpdoom never does).
     On the it2163 w2=128, h2=160. If you rebuilt from an older
     scaffold where lcd_appinit only clamped w1/h1, rebuild.
  BLUE  + "scanning"    -> alive; enumerating the SD folder. Stuck
     here = SD/FAT problem (rebuild with LIBC_SDIO=0 for USB logs).
  MENU (black, white     -> everything up to and including FAT works.
     text, teal bar)        Navigate with UP/DOWN, launch with OK.
  RED + "no .jar files"  -> the app runs fine but the game folder is
     + checklist text       empty or wrong (config.txt $@ rule broken,
                           so --dir never reached us and the scan saw
                           the SD root). The screen lists what to

Memory map (PSRAM, within fpdoom's allocation)
----------------------------------------------
  fpdoom code+data      ~700 KB
  fpj2me .text/.rodata  ~220 KB (VM+bridge+tinfl+PNG decoder)
  fpj_objects           128 KB (32k handles)
  fpj_heap              1 MiB Java heap (GC arena)
  fpj_stack              64 KB interpreter frame pool
  meta arena             512 KB class metadata (bump)
  fp_screen              40 KB back buffer @128x160
Total ~2.7 MB of 4 MB — same envelope fpdoom runs Doom in.

MIDP conformance notes (verified against the JSR-118 javadoc)
------------------------------------------------------------
  * Sprite.TRANS_* values 0..7 match the spec's constant-values page
    exactly (TRANS_ROT180=3, TRANS_MIRROR_ROT270=4, TRANS_ROT90=5,
    TRANS_ROT270=6, TRANS_MIRROR_ROT90=7). Games inline these.
  * Canvas.getGameAction() returns the OFFICIAL action codes
    (UP=1, LEFT=2, RIGHT=5, DOWN=6, FIRE=8, GAME_A..D=9..12) — NOT the
    negative device keycodes (those are only what keyPressed receives).
  * GameCanvas.getKeyStates() bits are 1 << action code, latched since
    the previous call, and digits 2/4/6/8/5 count as the nav pad.
  * Keypad: digits '0'-'9'/'*'/'#' are ASCII; nav = -1..-5, soft
    keys = -6/-7 (de-facto Nokia/SE values all 2007+ GL builds use).
  * Raw pad codes (0x04 UP, 0x08 LSOFT, ...) are fpdoom's KEYPAD_ENUM
    from syscode.h — if a key is dead on your handset, adjust the one
    table in src/fp_platform.c.

Known limitations (the M2 list)
-------------------------------
  * GLLib IGP splash: jars without their JAD (AC1's) lack the IGP
    config properties, so Gameloft's IGP sits at a black splash
    (state 18) instead of advancing. Needs JAD property defaults +
    the dataIGP/GAM unpacking path (the GL packed-image codec is
    pure Java in the jar; it runs, but its input chain never fires
    without the IGP config).
  * Exceptions are single-threaded: a throw unwinds to the nearest
    handler on the SAME frame chain; catch of interfaces works;
    finally is a catch-all handler (javac's pattern). No
    InterruptedException on Thread.sleep, no exception across the
    cooperative thread boundary (a throw inside run() kills that
    thread with a log).
  * Thread.start() is cooperative/inline: no preemption, no second
    start() while one run() is live (same single loop). Timer/
    TimerTask are still no-ops (listed as known libs only).
  * Missing library natives (anything not in the registry) are
    logged NO-OPS with zeroed returns — boot continues; implement
    the ones your game actually needs (the "native missing" log
    lists them).
  * java/lang/String has no classfile: strings ARE char[] objects;
    `new String(...)` is not supported (literals + valueOf are).
    Fixed properly by the M2 boot.jar (real java.* classfiles).
  * RecordStore.enumerateRecords returns null.
  * Media is silent by design (no audio HW bring-up).
